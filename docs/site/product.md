# 作品集网站产品文档

> 整理日期：2026-11-13。本文根据当前页面底稿、个人与项目事实、站点注册表及页面设计说明整理，供整体理解网站、审核范围和后续设计实现使用。
>
> 本文维护全站目标、读者路径和页面职责，并摘要说明各页内容。逐字文案与完整案例叙事仍以各页 `content.md` 为准；通用设计值、页面设计、证据缺口和审核状态继续在原入口维护。本次整理不代表新增文案、设计或整站实现已获确认。

## 1. 网站定位与目标

这是 Meng Wen 的个人作品集网站，是求职简历的补充材料。

求职方向以**产品经理（具备 UI/UX 背景）**为主，复杂业务系统是能力基础，医疗是已有经验的主要场景。网站通过真实案例，让读者判断作者能否把分散在人员经验、业务规则和协作过程中的要求，整理为可执行的系统，并完成流程、交互与界面方案。

网站承担求职沟通的第二跳：HR 或猎头先在简历中判断岗位、年限、行业与项目关键词，再将链接交给用人经理。进入网站的读者通常已经看过简历，会直接选择最相关的案例验证深度。

| 阅读阶段 | 要帮助读者完成的判断 | 对应产品目标 |
| --- | --- | --- |
| 进入首页 | 这是谁，主要做什么，哪个案例与岗位相关？ | 用约 5—10 秒交代身份与方向，提供清楚的案例入口 |
| 阅读一个案例 | 是否理解现场，能否解释关键判断，实际承担了什么？ | 通过背景、取舍、方案、证据与边界支持能力判断 |
| 阅读后 | 是否值得继续交流，如何联系？ | 提供明确、可使用的联系渠道 |

单次访问以一个案例为主，约 10 分钟内读完一个是当前阅读场景的推断目标，不是已有阅读时长统计。产品成效首先通过读者是否看懂业务、判断与证据来验收；现有资料未建立访问量、停留时长或联系转化率基线，本文不补设量化 KPI。

定位依据：[作品集中心](../../AGENTS.md#作品集中心-portfolio-center)、[个人概览](../profile/overview.md)、[投递沟通规则](../profile/outreach-guidelines.md)。

## 2. 读者与核心使用路径

主要读者是已经看过简历的用人经理；转交链接或协助判断的 HR 是次要读者。案例需要让不熟悉儿童口腔业务的人独立读懂，先解释服务对象、业务对象和旧工作方式，再展开规则与系统方案。

| 进入方式 | 阅读路径 | 必须支持的行为 |
| --- | --- | --- |
| 从简历进入首页 | 首屏识别 → 按需查看职业历程 → 选择一个案例 → 联系 | 首页导航、清楚的项目价值短句、独立详情入口、联系渠道 |
| 从简历或转发链接直达案例 | 项目背景与职责 → 关键判断与对应方案 → 结果与边界 | 案例自包含、章节目录、正文证据、章节定位 |
| 回到已关注的内容 | 直达案例或章节 → 查看相关文字与图片 → 返回继续阅读 | 保留章节深链接与兼容入口；图片查看结束后可继续原位置阅读 |
| 读完一个案例后继续了解 | 返回首页项目区 → 选择另一案例或联系 | 返回入口与浏览器历史行为可用，不强迫按案例顺序阅读 |

三个主案例是并列的能力证据，读者可以只读其中一篇。业务中的前台、医生、护士、财务和运营是案例所述产品的使用者，应与作品集网站的招聘读者区分。

## 3. 全站范围与信息架构

首页采用已确认顺序：

```text
首页
├─ 首屏：姓名与产品主张
├─ 职业历程：四阶段真实经历与能力锚点
├─ 精选项目
│  ├─ 会员与收银自动化
│  ├─ 咬合筛查与正畸协作
│  └─ PACS 读片与 AI 辅助
└─ 联系：邮箱与微信

独立详情与研究入口
├─ 三个主案例详情
├─ 接诊预习：候选案例，不进入首页三卡
└─ 会员办理章视觉实验：仅本地保留的单章实验
```

以上是当前资料范围的概览。页面 ID、准确路由、准入与来源映射统一查阅[站点注册表](content-map.md)，不能根据首页三张卡推定项目资料只有三个。当前项目事实库包含会员、正畸、PACS 与接诊预习四项；视觉实验复用会员材料，不算第五个业务项目。

当前优先完善 PC 中文版。移动端专项在整体确认后统一推进，英文入口暂停，既有资料保留供需要时恢复。实现与资料目录职责见[站点结构](structure.md)。

## 4. 首页内容与功能

首页负责身份识别和作品选择。其内容按四个区块组织，完整文案见[首页底稿](../pages/homepage/content.md)，构图、动效和当前封面采用见[首页设计](../pages/homepage/design.md)。

| 区块 | 内容依据 | 对读者的作用与功能要求 |
| --- | --- | --- |
| 首屏 | 姓名 `WEN MENG`；主张“把复杂业务，拆解为清晰、可用、可落地的产品系统。” | 迅速识别作者与方向；保留向下提示进入职业历程；首屏不放已移除的双 CTA |
| 职业历程 | 四阶段倒序经历，日期、职位与每阶段能力取自底稿及履历事实 | 用真实经历锚定能力；不扩写成第二份简历，不把全部工作年限算作产品年限 |
| 精选项目 | 按会员、正畸、PACS 排列；每卡保留项目名、价值短句和完整案例入口，配当前采用的封面 | 帮助选择相关案例；详细问题、个人职责和结果证据留在详情页 |
| 联系 | “欢迎直接交流。”及既有邮箱、微信 | 联系方式可读取和复制；操作反馈就近显示，失败时仍能获取渠道文字 |

顶部导航按“职业历程 → 精选项目 → 联系”排列。首页大姓名完全离开视窗后，顶部独立姓名出现，点击返回首屏；大姓名重新进入视窗时隐藏顶部姓名。姓名动效保留可识别的语义文字和静态回退，能力不足或减少动态时仍可阅读。

首页项目卡的展示名称与案例底稿标题可以因用途不同而简短，不据此改写项目事实。卡片封面承担识别与选择作用，真实系统证据在详情中说明来源与证明范围。

首页当前身份和履历文字与最新对外求职口径的差异，登记于[当前计划的冲突与待核实项](../superpowers/plans/current/2026-09-30-architecture-simplification-and-single-source-of-truth.md#规范整理后的冲突与待核实项)。本文采用全站目标定位概括，不代替用户决定首页逐字表述。

## 5. 三个主案例的内容要求

一篇案例只证明一件事，但可以用多个相互关联的设计判断支持这一主张。以下是底稿摘要和阅读要求，不是新增的章节模板，也不直接等于最终网页分区。

### 5.1 会员自动化与财务治理

**核心主张：把散在人脑里的规则变成系统边界，并兜住失败。**

面向连锁儿童齿科门店前台。家长补差价升级会员卡，看似一笔支付，实际牵涉原卡、服务权益、收费账单与优惠规则。旧流程中，这些信息在原系统不同模块里，前台负责查找对应关系、计算费用并分别操作；额外优惠的审批又难以跟上现场办理。

团队保留原门诊系统，在新入口中组织会员办理，再通过原系统接口执行相关操作。这缩小了自建范围，也保留了历史数据不完整、接口响应与人工接续的约束。

| 叙事内容 | 必须讲清的判断与机制 |
| --- | --- |
| 项目概览与背景 | 会员升级为什么需要同时处理卡、服务与账单；为什么保留原系统 |
| 办理依据与信息组织 | 先确认患者当前拥有什么，再核对本次目标卡、权益和费用；将原本靠记忆串联的信息组织在办理过程中 |
| 不确定账单 | 对应唯一时自动处理，多笔候选由前台依据记录确认，找不到则回原系统核对；自动化以可靠依据为前提 |
| 执行中断 | 按项说明已完成与待处理内容，提示人工去哪里继续；已完成操作保留，没有整笔自动回滚机制 |
| 优惠授权 | 区分活动优惠券与额外手动优惠；将逐笔授权改为个人月度额度，在费用确认处落实超额限制 |
| 落地与边界 | 分开说明推广范围、现场耗时观察、定性反馈、已实现能力，以及原系统和人工工作仍然存在的范围 |

作者负责一线调研、规则梳理、产品方案、流程交互与界面设计，并参与推进落地；整体改造范围由团队共同决定，业务规则与财务共同确认，研发负责系统实现。

底稿记录从六家试点推广到全连锁二十多家门店，典型升级办理由约四五分钟缩短至约一分钟。耗时来自一线调研与现场观察，没有统一严格计时实验；推广不代表全员采纳。个人额度规则已实现，但管理改善尚无量化对比。额度用完没有追加审批继续优惠的路径，限制也不能覆盖绕过新入口的所有改价行为。

七张真实界面设计稿支持信息组织、人工选择、输入约束与逐项反馈；展示数据为虚构示例，不能当作实际交易或故障日志。优惠使用看板仍缺对应界面。财务对账估算、宏观经营结果与个人反思按既有决定不公开。

内容依据：[会员底稿](../pages/member-automation/content.md)；事实核对：[会员项目资料](../project/会员自动化.md)；页面组织与证据展示：[会员设计](../pages/member-automation/design.md)。网页中的系统称呼遵循底稿维护说明所记录的“原系统／新系统”口径。

### 5.2 咬合筛查与正畸协作

**核心主张：能改协作机制，不只改界面。**

项目从矫正前的患者筛查入手。原有快筛、面型发育评估与门店会议较为分散，表单混合不同专业角色的任务，后续沟通和跟进过程难以持续追踪。

| 底稿章节 | 要让读者理解的内容 |
| --- | --- |
| 项目概览 | 为什么要把筛查变成持续动作，项目范围、职责、协作与试点周期 |
| 问题分析 | 旧流程如何运作；任务要求与执行角色不匹配；过程反馈为什么滞后 |
| 我的判断 | 识别并整合快筛入口；按角色和场景拆任务；按优先级分批推荐，并区分推荐候选与实际执行任务 |
| 整体方案 | 统一推荐规则，护士、儿牙医生与正畸医生接续同一记录，报告承接现场讲解与离店后的家庭沟通 |
| 落地与业务结果 | 关联筛查及后续收费节点，使进展可追踪；交代上线范围、运行记录和同期业务变化 |
| 反思 | 最小信息集要匹配接诊负担；入口整合要看实际使用；流程变更需要业务共同推进 |

作者负责门诊调研、流程和协作规则、PRD、交互界面设计，以及任务拆解、排期跟进和上线协调；医疗专业结论由正畸医生负责，沟通与转化由门店和业务团队共同推进。

推荐是在患者原有预约中增加筛查项目，不是另约一次就诊；推荐池也不等于当天实际任务。角色接续图应表达共同完善记录，不自行补出未经确认的临床先后顺序。

项目于 2026 年 2 月在全部门店上线；累计 18,460 条提交结论是记录量，未确认独立患者去重。全门店同期需矫成交率由 2025 年 2—4 月约 30%—40%，变为 2026 年 2—4 月约 50%—60%；这是判定需矫后产生矫正收费的患者占比，不能与累计漏斗混用，也不能全部归因于本项目。具体统计与素材缺口回原入口核对。

内容依据：[正畸底稿](../pages/orthodontics/content.md)；事实核对：[正畸项目资料](../project/正畸筛查与状态管理.md)；页面组织与关系图：[正畸设计](../pages/orthodontics/design.md)。

### 5.3 PACS 读片与 AI 辅助

**核心主张：在专业场景里为 AI 划出人机边界。**

PACS 在本案例中指影像查看与读片相关系统。原系统能推荐拍片，却无法记录拍片后是否完成读片。项目先建立标记、结构化记录、完成状态与病历同步，再让 AI 为医生提供可复核的异常线索。

| 底稿章节 | 要让读者理解的内容 |
| --- | --- |
| 项目概览 | 补齐的是拍片后的读片记录与管理过程；基础读片与 AI 部分的个人职责不同 |
| 问题 | 管理侧看不到完成情况；医生讲解缺少与影像位置对应、可再次查看的记录 |
| 我的判断 | 已填内容不再重复录入病历；记录融入讲片过程；AI 正确性与本次是否记录分别判断 |
| 方案 | 完整内容随检查表同步；标记与文字卡片对应，支持搜索、筛选与内容复用；医生选择如何处理 AI 提示 |
| 流程与机制 | 从拍片到病历的路径、未读／不完整／已读状态、影像类型和无法判读等特殊情况 |
| 结果 | 分开呈现已上线能力、管理目标和真实使用数据 |
| 反思 | 少打字不等于更快；AI 判断正确不等于必须记录；已有搜索与复用没有完全解决填写负担 |

基础读片由作者与产品经理共同推动，并与医疗主任确认规则；作者负责流程交互和界面设计，共同整理 PRD。AI 辅助部分由作者独立负责产品方案、规则、交互、UI 和 PRD，算法同事负责模型与识别，最终诊断由医生负责。

关键机制必须准确表达：

- “完成读片”检查内容完整性，不直接触发病历同步；已完成内容随检查表同步进入病历。
- 明确确认未见明显异常与“无法读片”分别处理，不能都视为未读或正常。
- 医生对 AI 提示有三种处理：正确且继续读片、正确但本次不写入病历、判断错误并删除。
- AI 仅支持已确认的影像类型；加载超过五秒或调用失败可手动继续，仍执行相同必填检查。

公开数据分别是 2024-10 至 2026-08 累计读片 147,793 张、AI 参与影像约 96.3%、医生删除 AI 记录 3,736 条。三项来自不同数据口径，不能拼成漏斗；AI 参与不是准确率或采纳率，删除也不等于判断错误。60% 是管理目标，未被证明已达到。未经核实的发现数增长与医疗效果不进入公开页面。

内容依据：[PACS 底稿](../pages/pacs-ai/content.md)；事实核对：[PACS 项目资料](../project/PACS读片与AI辅助判断.md)；页面组织、占位与图示：[PACS 设计](../pages/pacs-ai/design.md)。标题仍按底稿暂用，项目起止不以统计期推定。

## 6. 候选案例与视觉实验

### 6.1 接诊全流程预习与任务编排引擎

该项目资料独立于首页三卡，当前只以候选定位说明机制，不自动扩大为公开主案例。

内容围绕“跨系统信息分散 → 聚合患者全景 → 分层任务包 → 医护运协同 → 备注同步”展开。重点判断是推荐需要可解释、任务需要分层，以及牙位输入和时效校验需要贴合口腔场景。

底稿保留现场问题、解法、三个判断、机制证据、能力迁移与待补项。已有资料支持全景视图、推荐解释、角色校验、牙位控件及同步规则；项目周期、正式上线范围、采纳率和效率结果不足，不能将任务结构写成覆盖率或减少漏项的成果。其单篇主张与准入由原入口确认，本文不替候选案例定稿。

内容依据：[预习底稿](../pages/pre-visit-engine/content.md)、[项目资料](../project/接诊全流程预习与编排引擎.md)；候选呈现与状态：[预习设计](../pages/pre-visit-engine/design.md)；准入：[站点注册表](content-map.md)。

### 6.2 会员办理章视觉实验

复用会员已审核章节和同一组截图，检查更宽的证据展示、局部近读及不同构图，能否更清楚地表达信息集中核对、不确定账单交给人工、中断后明确进度三项判断。

实验仅在保留实验代码的本地环境直达查看，源码与路由不纳入本次正式提交；设计研究文档保留。不新增业务事实，不改变首页准入，也不将实验视觉自动推广到正式页或全站。范围、对照与呈现依据见[实验设计](../pages/design-experiment-membership/design.md)。

## 7. 全站功能与阅读体验要求

本节归纳已在底稿和设计说明中出现的产品行为，不另定像素值或统一所有案例的布局。

## 8. 内容、证据与公开边界

完整质量规则以[案例内容规范](../CASE_STUDY_SPEC.md)为准。全站整理与后续实现需保持以下边界：

1. **每篇独立成立。** 先解释业务与原工作方式，再展开方案；正文自身足以理解，图片补充证明。
2. **贡献与责任可区分。** 写清个人工作、共同确认、团队决策及专业角色责任，不将团队成果全归个人。
3. **判断有依据。** 重要取舍对应事实、真实记录、机制或界面；未知过程不补写为研究与迭代故事。
4. **结果分开表达。** 观察到的变化、已实现能力、推广范围、使用反馈与管理目标分别说明。
5. **数字保留口径。** 单位、周期、分母与限制跟随对应数字，跨表或跨周期数据不随意串联。
6. **素材有证明范围。** 界面稿说明信息组织与交互，示意图说明关系；样机与虚构展示金额不成为使用或经营证据。公开素材按已有脱敏要求处理。
7. **公开正文与维护说明分开。** 待核对事项、原始来源、制作要求与历史记录放维护层；影响理解数字和结论的限制则与正文就近呈现。

证据及素材缺口只在[内容就绪度清单](../project/content-readiness.md)维护。底稿中的新版确认可以修正旧事实记录；发现来源冲突时保留出处，不以旧素材或代码覆盖后续确认。

## 9. 验收与推进依据

网站产品验收检查以下问题：

| 层面 | 可据以判断的结果 |
| --- | --- |
| 全站定位 | 首页能快速解释作者与方向，三个入口帮助选择；没有通过新增内容改变求职定位 |
| 内容理解 | 读者能说清一个项目的对象、原问题、关键判断、作者职责与结果边界；可以只读一篇 |
| 信息呈现 | 图文关系和阅读节奏服务该页主张；证据能读清，数字的单位与限制可见 |
| 功能行为 | 当前页面适用的入口、目录、锚点、返回、图片查看和联系行为可用 |
| 规范一致性 | 全局采用值有来源，组件与局部特例边界清楚；符合规范与页面设计质量分别记录 |

内容确认、设计审核与实现验收分别进行。重要页面按“内容 → 设计推导与确认 → 实现”推进；明确的局部调整按既有授权执行。本产品文档整理不启动全站重设计或源码迁移。

各页实际状态见对应 `design.md` 的“验收与状态”；当前行动、依赖及待核实冲突见[当前计划](../superpowers/plans/current/2026-09-30-architecture-simplification-and-single-source-of-truth.md)。历史截图与测试只能说明当时版本，本次文档整理不构成页面回归验证。
