# 会员自动化页面设计说明

> 正式文案：[content.md](content.md)。通用采用值：[DESIGN.md](../../../DESIGN.md)。本页维护章节映射及旧深色实现的局部描述，V4迁移尚未开始；旧实现数值不能作为全局新指令。

## 1. 整体方向

当前实现保留深色大标题、左侧目录和连续正文。面向招聘方，先交代会员办理原来怎样运转，再说明为什么将常规交易自动处理、优惠改为额度校验，以及失败时如何保留权益。

本页重点是“交易规则与异常处理”，不是财务仪表盘。主要证据是办理界面和业务流程图；数字只在结果章出现，不新增分类标签、首屏指标卡、版本编号或能力标签。

**取舍：** 不把所有规则铺成一张巨大的规则矩阵，也不用大量状态卡取代正文。按三个判断逐步解释，最后用主流程串联；退卡等材料不足的细节不靠图形补齐。

## 2. 现行实现骨架与局部几何（仅本页旧实现）

现行桌面最大宽度 1320px，左右留白 32px。开场全宽，正文采用 180px 目录 + 64px 间距 + 其余正文区；文字最大宽度 760px，截图和流程图可展开到正文区全宽。

```text
返回首页                                             语言切换

会员自动化与财务治理（主标题）
项目介绍
──────────────────────────────────────────────────────────
我的职责与协作（小标题）
职责与协作说明
──────────────────────────────────────────────────────────
                会员升级界面／素材占位

目录                  正文与证据
01 项目概览           02 旧办理流程 + 三类问题
02 问题               03 判断 A、B、C（纵向）
03 我的判断           04 理由 → 界面 → 对应异常
04 方案               05 主流程与异常分支
05 系统机制           06 已上线能力 + 两组耗时对比
06 结果               反思暂不公开，等待本人补充
```

- 各尺寸开场均按标题、简介、职责纵向排列，左边界一致。简介和职责正文限宽 760px，职责使用小标题与细分隔线；目录仍叫“项目概览”，开场不另显示这一大标题。当前旧字阶不作为V4采用值；迁移时引用DESIGN.md §3.4。
- 角色用普通段落，不拆成职位、范围、状态的标签墙。项目周期未核对，不放空日期或用数据周期代替。
- 当前公开六个章节，沿用内容稿名称；反思等待本人补充，不显示章节或目录入口。概览就是开场，不在正文再重复一份；目录 01 跳回开场。
- 目录只在正文区域保持可见，点击定位标题并留出顶部安全距离。低高度桌面可滚动目录；手机不固定目录。
- 章节标题与正文共享左边线，宽图也从同一边线起；全宽开场是明确的例外，不穿插无理由的居中小标题。

## 3. 各章节怎么排

### 01｜项目概览

先标题和摘要，接角色段落，再放一张宽幅会员升级界面。界面应能说明原卡、目标卡、补差金额和权益，不增加悬浮数据卡遮挡字段。首屏不复制结果章的耗时数字。

### 02｜问题

先放旧办理流程示意，再纵向展开内容稿的三个问题。示意把查卡、账单、计算和权益处理连起来，让读者理解一次办理为什么需要反复核对；以注释标明“依据原业务流程整理”，不冒充历史截图。

三个问题用小标题、正文和细分隔线呈现，不做三张彩色痛点卡。图中只强调操作分散和异常判断，不编写访谈引语、错误次数或损失金额。

### 03｜我的判断

判断 A、B、C 分为三组纵向段落。每组先交代原有问题，再突出判断标题，末尾提供跳到 4.1、4.2、4.3 的文字链接。正文不折叠，读者不需要操作才能看见理由。

这三组是后文方案的索引，不在这里再画完整系统架构。个人提出与共同确认的边界待核对，视觉上不添加“独立主导”等归因标识。

### 04｜方案

每节顺序固定为“为什么这样处理 → 怎么实现 → 界面或规则示意”。图注紧跟证据，不将三段说明变成功能卡片清单。

- **4.1 常规办理与异常选择：** 主界面使用宽图，自动带入、必须确认、异常时选择的位置以少量编号标出。多账单与无账单提示用局部图补充；有效期规则变化用一行前后对照说明，不扩大为版本演进章节。
- **4.2 优惠额度：** 用一组紧凑规则示意对照“额度内允许办理 / 超额阻断并说明原因”，接对应截图与记录说明。没有具体额度，不填假金额，不画逐笔审批弹窗或杜撰财务后台。
- **4.3 失败回退：** 先解释为何要保留原卡与权益，再画“执行 → 成功反馈 / 失败保留”的两条业务路径。真实失败截图缺失时只展示规则示意，不显示虚构日志、接口次序或技术上的原子性承诺。跨店批处理限制保留在图注附近。

### 05｜系统机制

本章用一张业务主流程图串起 4.1–4.3，不重复每张界面。桌面按行向下展开，避免把七个节点挤进一条细长横线；手机直接纵向排。

```text
读取卡与账单 → 判断办理条件 → 匹配与计算
                       └ 信息不足／多账单 → 对应异常处理
                                 ↓
                         校验优惠额度
                       └ 超额 → 阻断并说明原因
                                 ↓
                         确认 → 执行办理
                                ├ 成功 → 展示结果与记录
                                └ 失败 → 保留原卡与权益，记录原因
```

上述是业务关系草图，不代表接口执行顺序。卡、账单、权益作为需核对的对象，以图旁简短说明出现，不绘制未经核实的数据表关系。

图后承接内容稿的异常表。桌面两列“情况 / 处理边界”，手机转为逐项上下说明，不省略跨店结算限制，也不将所有异常统一标为系统失败。

### 06｜结果

先用开放式文字行说明已上线能力，再纵向放两组耗时对比。每组都包含指标名、前后值、来源和适用范围，不做排行榜或折线趋势。

- **典型升级耗时：** 前值中性灰，后值 Mint，紧邻标注门店现场实测、典型升级结算场景。
- **财务对账反馈：** 同样保留前后值，但整体字号略小、数字使用中性文字，突出“财务团队估算”。不能与实测一起包装成两项精确 KPI。

不新增提效百分比、样本量、门店数量或实时分账成效。没有报表截图时，直接排版已有数据即可；数据不伪装成系统看板。

### 07｜反思

待用户补充真实反思后，使用窄幅正文、小标题和简短段落，不另加总结卡或个人能力标签，不把规则推演包装成上线故事。

公开边界与待办见§6。

## 4. V4目标与当前实现边界

V4目标引用DESIGN.md的Case Reader角色、容器与组件：深色封面、浅色连续正文、稳定阅读轴及真实功能反馈。具体呈现映射待首页与PACS校准后推进，不能将旧稿的深色全页、固定8px网格、H1/H2通用流式字阶当作新实施指令。

当前深色实现及已确认纵向开场保持；本页章节和业务关系不随视觉迁移变化。截图须完整保留字段，占位不显示假播放或缩放入口。流程一次呈现，hover不承载必读说明，reduce显示完整内容。

## 5. 现行响应式与素材边界

开场始终单栏。≥1200px 正文使用上述目录双栏；768–1199px 目录改为正文前的换行链接组，左右留白 24px。<768px 全页单栏、留白 20px，文字与图片使用可用宽度，章节间距 64–96px。

判断、结果与异常表改为纵向，不缩小字体硬塞进多列。流程连线仍表示相同分支关系，不把异常接成成功路径。所有触控入口至少 44px，表格与图示不能造成整页横向溢出。

待备素材以 content.md 就近备注为准：升级主界面、多账单或无账单提示、额度提示与记录、失败提示。已有数据与业务关系可以直接制作图，不要求用户另找结果截图。

缺图位置沿用“素材准备中 / Image pending”，展示图片名称与用途。预留稳定画面尺寸，真实素材到位后按其宽高比调整；不造会员卡、交易日志或财务截图来填空。证据缺口仍在 [content-readiness.md](../../project/content-readiness.md) 维护。
