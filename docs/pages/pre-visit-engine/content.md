# 一页案例 04：接诊全流程预习与任务编排引擎 (Pre-visit Orchestration & Task Engine)

> **项目 Slug**：`pre-visit-engine`  
> **页面定位**：扩展案例 / 机制进行中
> **证据状态**：有原始需求和规则机制，缺少可公开的上线结果与规模化采纳证据。

## 先看懂这个项目

- **问题**：网络电话、领健收费和 360 病史中的信息分散在不同系统，护士、医生和运营只能靠人工拼接和口头交接完成接诊前准备。
- **我的角色**：从 Product Designer 逐步承担 Product Owner / Designer 责任，主导全链路交互、业务规则推演、PRD 和技术协作。
- **核心判断**：先做一个全景视图聚合关键资料，再用结构化任务包承接推荐和分工；推荐必须能展开解释；牙位选择和时效校验要按口腔场景定制。
- **结果边界**：目前能证明的是跨系统整合、任务模型、可解释推荐、角色校验和病历同步机制；`100% 结构化任务包`、采纳率、减少漏项和效率提升仍待正式数据。

## 现场问题

接诊前需要同时了解家长诉求、既往病史、影像、卡券和预约信息。旧流程要求一线在多个系统之间切换，任务靠经验判断；如果系统只给出推荐而不说明原因，一线也难以判断是否值得执行。

## 我的解法

1. **全景视图**：聚合电话、收费、病史、预约和会员信息，先让团队看到同一份患者上下文。
2. **分层任务包**：将任务拆成必选、推荐和自定义扩展包，让标准化和现场灵活性共存。
3. **角色协同与校验**：护士确认资料，医生复核诊疗准备，运营跟进预约与权益；角色交接时校验必填项并定位首个缺口。
4. **病历同步**：把预习结果按约定格式回写领健备注，避免团队重复整理。

## 三个关键判断

### 推荐为什么要能解释？

- **选择**：主流程保持简洁，点击抽屉查看推荐条件和推导依据。
- **原因**：把隐性业务经验变成可检查的规则，降低“系统额外加任务”的不确定感。
- **边界**：可解释机制不等同于已证明推荐被采纳或提升效率。

### 为什么不用长表单，而用分层任务包？

- **选择**：必选、推荐、扩展分层折叠，按任务展开。
- **原因**：不同预约类型和角色需要的信息不同，一次铺开会增加认知负担。
- **边界**：任务包是否覆盖所有场景、是否减少漏项，仍需样本和上线记录验证。

### 为什么定制十字牙位控件？

- **选择**：支持全口、象限、连续牙段、单颗牙和多生牙选择，并处理互斥关系。
- **原因**：牙位是临床任务的关键输入，通用下拉框难以表达混合牙列和多生牙位置。
- **边界**：控件规则有原始需求支持，但尚缺可公开的实际使用反馈。

## 机制证据

`电话 / 收费 / 病史 → 全景视图 → 规则推荐任务包 → 医护运协同 → 领健备注同步`

预习可以提前 1—3 天完成，因此需求中保留了超过 7 天的重新确认弹窗；跨系统数据变化、退改签、资料缺失和同步失败需要在正式实现材料中继续补充验证。

## 能力迁移

这个项目体现的是“设计驱动产品建模”：当交互无法承载复杂业务时，先通过状态、任务包、牙位控件和解释抽屉把规则显性化，再反向收束 PRD 和系统边界。
