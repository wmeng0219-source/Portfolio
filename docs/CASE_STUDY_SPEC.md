# 作品集案例内容规范

本文件是现有及未来案例的通用内容质量依据。审核稿从[文档入口](README.md)进入对应`content.md`；事实以`docs/project/`为准，原始材料仅用于追溯。协作顺序和文档职责见[AGENTS.md](../AGENTS.md)，通用视觉采用值见[DESIGN.md](../DESIGN.md)。

## 1. 案例需要证明什么

作品集定位是**具有设计背景的复杂业务系统产品经理**（Product Manager for Complex Systems, with a Design Background）。案例应让读者理解真实现场、规则与角色关系，看到可解释的产品判断、落地过程和可靠证据。界面、系统图与动效是证明判断的材料，不以页面或模块数量衡量质量。

## 2. 必要质量要求

以下是证据关系，不是固定章节模板。按项目事实和用户确认的内容组织，可合并区块；不强制章节数、V1/V2、首屏战果、Bento、GSAP或独立反思章。

| 证据关系 | 应回答的问题 | 质量边界 |
| --- | --- | --- |
| 现场与代价 | 谁在什么场景遇到问题？原机制如何运转，断点造成什么损失？ | 写可观察的表现，避免只说“复杂、低效、体验差”；规模有证据才写 |
| 问题判断 | 现象与根因有什么区别？方案要改变什么机制？ | 说明依据，不用抽象口号代替因果；判断句可放标题或正文，不强制统一句式 |
| 职责与约束 | 本人负责哪些判断和交付？与团队怎样分工？ | 岗位名称不足以证明职责；时间、资源、技术、专业或组织限制按实际写 |
| 机制与取舍 | 规则、状态、流程或角色怎样承接业务？为什么选择该方案？ | 展开关键判断及相关代价、异常或兜底，不用功能清单代替推理；不补编被否决方案 |
| 落地与变化 | 方案怎样进入使用，哪些角色改变了做法？ | 试点、灰度、培训、阻力、版本迭代只写真实发生的内容 |
| 结果与边界 | 结果能回扣哪个问题？证据能证明什么、不能证明什么？ | 区分业务结果、系统能力与组织价值；没有可靠数字可用机制或使用证据，不造量化成果 |

### 2.1 事实与归因

- **已确认事实**：已上线功能、实际数据和已发生决策使用确定语气。
- **设计推理**：说明观察、访谈或规则分析依据，不能包装成用户研究结论。
- **假设与未验证方向**：明确标注，不写成已实现能力或成果。

不虚构研究、反馈、数据或失败，不把团队成果全部归为个人，不把相关性写成单一因果。隐私材料可匿名或概括来源类型，不能因不可公开而补编证据。

### 2.2 数字与来源

每个公开数字保留已有且适用的口径，缺口明确留在证据入口，不用看似精确的结论掩盖不确定性。

| 字段 | 要求 |
| --- | --- |
| 指标名称 | 测量的对象和含义 |
| 分子/分母 | 转化率、完成率、检出率等比例必须区分 |
| 人群/样本 | 门店、患者、影像或交易类型等适用范围 |
| 时间范围 | 观察周期或前后对比时间 |
| 数据来源 | 埋点、报表、抽样、现场实测、人工统计或团队估算 |
| 归因限制 | 外部变量、样本限制，以及可以和不能支持的结论 |

口径不完整时使用准确的“约、阶段性数据、平均记录数”等表达，且保留限制。管理目标、使用规模与效果分别说明；不同单位或周期不串成漏斗。平均每张影像发现数增加不等于医学检出率提高，应区分发现数、召回率、准确率与漏诊率。现场实测和团队估算不能包装成同等级精确KPI。

“调研显示、一线反馈、上线后改善”等表述应能追溯来源、对象范围和时间。研究或试点有相关材料时，记录参与角色、任务、评价标准与据此形成的判断。

### 2.3 素材与图注

选择能证明现场、机制、判断或结果的素材，不以图片数量作为完成标准。每张图配就近图注，说明业务意义、来源范围及必要脱敏；关系示意不能冒充系统截图，缺图不能用装饰图或假产品证据补数。图示要有文字解释，不能用图替代推理。

### 2.4 文案与双语

- 当前按用户2026-10-15决定先完善PC中文，确认后再做移动端；英文暂停且非必需。暂停期间新增文字先做中文，不强制同步翻译；保留既有英文资料，未来启用时再按语境转译与审核。
- 标题优先帮助扫读；用途型、判断型标题按实际层级选择，不要求每个标题都是结论句。
- 每段聚焦一个因果关系，避免堆叠“系统化、闭环、赋能、提升”等抽象词。
- 不把目标写成结果、功能数量写成价值、个人推演写成上线故事。

## 3. 按需增强

| 模块 | 何时适用 | 应呈现什么 |
| --- | --- | --- |
| Design Craft | 视觉或交互是项目价值的重要部分 | 色彩/组件的业务语义、认知负荷、渐进暴露、反馈容错与责任边界；不泛列设计参数 |
| 迭代与版本 | 存在真实演进和判断变化 | 阶段间为何调整及依据；无V1/V2时可写推进阶段或机制演进 |
| 系统模型 | 状态、权限、规则、数据或任务关系需要解释 | 已确认关系、异常与边界，配文字推理 |
| 界面走查 | 连续界面能证明关键决策 | 原有/新方案、正常/异常或端到端操作；不展示无论点的全量截图 |
| 研究与试点 | 有可回溯材料且与判断相关 | 观察、任务、反馈及它怎样改变决策 |
| 反思 | 有真实学习、未验证判断或可讨论的后续取舍，且获准公开 | 结论适用范围与重做时会先改变的判断；可融入结果或结尾，不编失败，不以“继续优化”代替具体学习 |

反思不是每个主案例的机械必填章。会员案例按用户决定暂不公开反思，待本人提供并确认后再加入；不能用本规范覆盖该决定。

项目类型决定展开重点：复杂业务系统重规则、状态、治理和角色协作；体验优化重研究、交互变化及验证；从0到1重机会、MVP和落地；AI与专业工具重人机责任、置信度、异常及专业控制权。具体案例事实与章节仍由对应内容稿决定。

## 4. 审核判断

合格案例应让读者回答：为什么需要改变、根因是什么、本人做了哪些判断及取舍、机制怎样在组织中运行、结果怎样测量且有哪些局限。按现有事实和已确认公开范围核对，不为齐全模板补入未知章节、数据或故事。
