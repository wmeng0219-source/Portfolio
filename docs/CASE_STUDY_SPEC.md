# 作品集案例内容规范

> **版本**：2.0 · 2026-08-07<br>
> **适用范围**：现有及未来新增的产品案例，包括会员自动化、正畸筛查、PACS AI 及其他复杂业务系统项目。

## 1. 这份规范要证明什么

本作品集的核心定位是：

> **具有设计背景的复杂业务系统产品经理**

英文表达：

> **Product Manager for Complex Systems, with a Design Background**

案例需要证明的不是“做过多少页面”，而是能够：

1. 理解真实业务现场及其约束。
2. 把模糊问题拆成规则、流程、状态和角色关系。
3. 在多个利益相关者之间做出可解释的产品判断。
4. 推动方案进入真实使用，并用可靠证据说明变化。

视觉设计、交互细节和系统图是证明判断的材料，不是案例存在的目的。

## 2. 三层文档边界

案例整理始终按以下顺序工作：

```text
项目事实层  →  案例叙事层  →  页面呈现层
```

### 2.1 项目事实层

唯一事实来源是 `docs/project/`。原始材料保存在 `docs/origin/`，用于追溯，不直接作为页面文案。

事实至少分为三类：

| 类型 | 含义 | 写法 |
| --- | --- | --- |
| 已确认事实 | 已上线功能、真实流程、实际数据、已发生决策 | 使用确定语气 |
| 设计推理 | 基于访谈、观察或规则分析形成的判断 | 明确写出依据 |
| 假设/未验证 | 未来方向、未上线方案、待确认规则 | 标注为假设或后续方向 |

禁止把讨论方案写成已上线成果，禁止把团队成果全部归为个人，禁止虚构调研、数据或用户反馈。

### 2.2 案例叙事层

案例叙事负责回答：为什么做、发现了什么、为什么这样设计、如何落地、带来了什么价值。

### 2.3 页面呈现层

页面视觉遵循根目录 `DESIGN.md`。Bento、GSAP、吸顶、瀑布流和其他动效属于表达手段，只有在能帮助理解信息时才使用，不是内容合格条件。

## 3. 所有案例的核心证据链

每个案例必须形成以下六段链路。可以合并区块，但不能缺少其中的证据关系。

```text
现场与代价
   ↓
问题判断与设计命题
   ↓
我的职责与约束
   ↓
关键机制与产品决策
   ↓
落地、协作与异常处理
   ↓
结果、指标口径与局限
```

### 3.1 现场与代价（Context）

回答：谁在什么场景下遇到了什么问题，问题造成了什么业务或临床代价？

至少写清：

- 主要角色及其目标：如医生、前台、财务、运营、管理者。
- 原有流程或机制如何运转。
- 断点、冲突或信息断层在哪里。
- 问题规模、频率或影响范围（若有可靠数据）。

避免只写“流程复杂”“体验不好”“效率低”等结论，必须给出可观察的现场表现。

### 3.2 问题判断与设计命题（Diagnosis）

先区分现象和根因，再用一句话定义设计命题：

```text
现象 → 根因 → 影响 → 设计命题
```

推荐句式：

> 将 `[旧的业务机制]` 转化为 `[新的可执行机制]`，从而解决 `[关键损失]`。

### 3.3 我的职责与约束（Scope）

不要只写职位名称。明确：

- 我负责的判断和交付物。
- 与产品、设计、研发、业务或算法团队的边界。
- 时间、技术、合规、资源或组织约束。
- 哪些结果是我直接推动的，哪些是团队共同完成的。

### 3.4 关键机制与产品决策（Mechanism & Decisions）

用 2-4 个关键机制解释系统如何承接业务。每个机制至少包含：

1. 原有做法及其失效原因。
2. 可选方案或被否决的方向。
3. 选择标准：效率、风险、可控性、学习成本、可扩展性等。
4. 最终方案及其代价。
5. 异常状态、权限边界和兜底路径。

决策不是“我设计了 X”，而是：

```text
约束/风险 → 方案 A 与方案 B → 判断标准 → 选择 → 剩余代价与兜底
```

### 3.5 落地、协作与迭代（Delivery）

只有在真实发生过时才写 V1/V2。若项目没有明显版本迭代，可以写“推进阶段”“试点到全量”或“机制演进”，不要为了符合模板虚构版本。

建议说明：

- 谁需要改变工作方式。
- 如何处理业务阻力和利益冲突。
- 是否试点、灰度、双轨运行或分阶段上线。
- 上线后根据什么反馈调整。

### 3.6 结果与证据（Impact）

结果至少分为以下一类，最好能覆盖两类以上：

- **业务结果**：转化、收入、成本、处理时长、覆盖规模。
- **系统能力**：状态可追踪、规则可配置、流程可观测、异常可审计。
- **组织价值**：角色边界清晰、协作成本下降、管理方式改变。

每个数字必须同时注明：

| 字段 | 要求 |
| --- | --- |
| 指标名称 | 说明到底测量什么 |
| 分子/分母 | 尤其是转化率、完成率、检出率 |
| 人群或样本 | 门店、患者、影像类型、交易类型等 |
| 时间范围 | 上线前后或具体观察周期 |
| 数据来源 | 埋点、业务报表、抽样、人工统计等 |
| 归因边界 | 能证明什么，不能证明什么 |

没有完整口径时，使用“约”“阶段性数据”“平均记录数”等准确表述，不使用看似精确但无法解释的结论。

特别注意：平均每张影像的发现数量增加，不等于医学意义上的检出率提升；必须区分“发现数、召回率、准确率、漏诊率”等概念。

## 4. 项目类型与重点模块

所有项目共享核心证据链，但不要求使用完全相同的章节比例。

| 项目类型 | 主要证明能力 | 应重点展开 | 可选模块 |
| --- | --- | --- | --- |
| 复杂业务系统 / B 端 | 业务理解与系统机制 | 状态、规则、角色协作、治理、推进 | Design Craft、完整 UI 走查 |
| 用户体验优化 | 问题发现与体验验证 | 研究、痛点、交互变化、可用性证据 | 组织机制、长期运营 |
| 从 0 到 1 | 机会判断与产品落地 | 目标用户、MVP、验证、迭代、结果 | 复杂权限或治理 |
| AI / 专业工具 | 人机边界与风险控制 | 责任、置信度、异常、反馈闭环、专业 UI | 数据飞轮、模型协作 |

## 5. 可选增强模块

以下模块按项目事实选择，不做全站强制：

### 5.1 设计体系与 UX 手艺（Design Craft）

当视觉或交互本身是项目价值的重要组成时再加入。可写：

- 色彩和组件的业务语义。
- 视线层级、认知负荷和工作环境。
- 渐进式暴露、快捷操作、反馈和容错。
- 关键组件如何支撑规则、状态或责任边界。

不要泛泛罗列颜色、圆角、字体或“符合某标准”，必须说明它如何改变决策或减少风险。

### 5.2 迭代与版本演进

展示真实的判断变化，例如：

- 从单点功能转向机制。
- 从全量推送转向优先级调度。
- 从人工审批转向规则边界。
- 从 AI 自动化转向人机协作。

### 5.3 系统模型

根据项目选择状态模型、权限模型、规则模型、数据模型、任务机制或流程图。图示必须有文字解释，不能用图替代推理。

### 5.4 界面全景

展示能够证明关键判断的界面即可。优先展示：

- Before / After 对比。
- 关键状态和异常状态。
- 端到端流程中的连续界面。
- 能解释系统关系的架构图或数据图。

不以图片数量作为完成标准。

### 5.5 研究、验证与素材证据

案例中的“调研显示”“一线反馈”“上线后改善”等说法必须有可回溯的证据来源。可公开时，至少记录一种：

- 访谈或现场观察：对象角色、数量或场次、观察时间与关键发现。
- 数据分析：报表名称、查询口径、样本范围与观察周期。
- 可用性或试点评估：参与门店/角色、任务、通过标准与主要反馈。
- 推进过程：灰度范围、双轨周期、培训或业务阻力，以及据此做出的调整。

不便公开的材料可以匿名、概括或只说明来源类型；没有来源时只能写为个人设计推理，不能包装成用户研究结论。

每个主案例应准备能够支撑叙事的素材组合，而非只放封面图。优先级为：

1. 旧流程、原始界面或问题现场。
2. 关键状态、规则、角色协作或决策对比图。
3. 最终界面或端到端流程走查。
4. 指标、试点或上线后的真实使用证据。

每张素材必须有图注，说明它证明的判断、来源范围和必要的脱敏处理。素材不够时，减少展示区块，不用装饰图补数。

### 5.6 反思与结论边界

每个主案例结尾必须包含简短 Reflection，回答：

- 什么判断得到验证，什么仍未验证？
- 哪个限制、外部变量或组织条件影响了结果？
- 如果重新开始，会先改变哪一个判断、试点或衡量方式？

反思不是自我否定，而是明确结论的适用范围。它不得编造失败，也不得用“继续优化”替代具体学习。

## 6. 三个现有项目的整理重点

### 6.1 会员自动化与财务治理

**核心命题**：把依赖人工经验的优惠与结算规则，变成可执行、可审计的交易系统。

必须优先补强：

- 一个真实的跨门店升级或复杂收银场景。
- 人工审批、额度引擎和异常抽检之间的取舍。
- 规则命中、跨店结算、退款或超额优惠的边界。
- 20+ 门店如何试点、推广和统一规则。
- “4-5 分钟 → 1 分钟”“3 天 → 1 天”的统计口径。

Design Craft 可以服务于高频收银和错误预防，不必独立扩写成视觉系统章节。

### 6.2 正畸筛查与状态管理

**核心命题**：把一次性的线下面评活动，重构成按发育窗口持续运转的患者漏斗。

必须优先补强：

- 旧流程中儿牙、正畸、护士和运营的断点。
- 为什么取消快筛，以及新旧流程的责任变化。
- 状态模型、再筛查触发和动态优先级。
- 转诊激励如何由系统留痕承接。
- 明确每个转化指标的分母：例如“需矫 → 预约”与“推荐 → 预约”不能混称。

此项目的主视觉应是流程、状态和漏斗，不是 UI 组件展示。

### 6.3 PACS 读片与 AI 辅助判断

**核心命题**：先让读片行为可追踪，再让 AI 在不越过医生责任边界的前提下提高发现量。

必须优先补强：

- V1 如何建立三态留痕，V2 如何引入人机复核。
- 全景片不启用 AI、超时降级、类型前置确认等边界。
- “确认但无需写入病历”如何同时保护病历质量和训练数据。
- AI 结果、医生判断和病历写入之间的责任关系。
- 将“平均发现数提升”与“检出率”分开表述，并补充样本与周期。

这是三个项目中最适合完整展开 Design Craft 的案例。

## 7. `src/data/projects.js` 建议数据契约

数据结构服务于内容事实，不强迫每个项目填满所有字段。字段缺失时，页面应隐藏对应模块，而不是填充空泛文案。

  role: { zh: '...', en: '...' },
  context: {
    zh: '...',
    en: '...',
    stakeholders: [/* 角色与目标 */],
    constraints: [/* 真实约束 */]
  },
  diagnosis: { zh: '...', en: '...' },
  mechanisms: [
    {
      title: { zh: '...', en: '...' },

      tradeoff: { zh: '...', en: '...' },
      edgeCases: [{ zh: '...', en: '...' }]
    }
  ],
  delivery: { zh: '...', en: '...' },
  designCraft: { /* 可选 */ },
  process: [ /* 只有存在真实演进时填写 */ ],
  impact: {
    metrics: [
      {
        name: { zh: '...', en: '...' },

## 8. 双语与文案规则

- 页面新增的用户可见文本必须提供中英文。
- 中文先保证事实和逻辑，再做英文转译；英文不追求逐字对应。
- 标题描述判断，正文补充依据，标签只承担分类。
- 每段只表达一个因果关系，避免连续堆叠“系统化、闭环、赋能、提升”等抽象词。
- 禁止把目标写成结果，把功能数量写成价值，把团队成果写成个人独立成果。

## 9. 发布前检查清单

### 事实与归因

- [ ] 每个数字都有分母、范围、周期和来源。
- [ ] 已上线、推理和假设已明确区分。
- [ ] 个人职责边界真实可辩护。
- [ ] 没有把相关性写成因果性。
- [ ] “调研、反馈、试点”均能追溯到来源、范围或准确的证据类型。

### 叙事与判断

- [ ] 首屏一句话能说明旧机制到新机制的变化。
- [ ] 能看出真实角色冲突和业务代价。
- [ ] 至少有 2 个关键决策，而不是功能清单。
- [ ] 至少一个决策包含被否决方案、代价或异常兜底。
- [ ] 结果能回扣最初的问题，而不是只展示漂亮数字。
- [ ] 有一段说明验证边界与下一次会改变的判断。

### 页面与视觉

- [ ] 页面遵循 `DESIGN.md` 的视觉系统。
- [ ] 图示和界面服务于叙事，能够解释流程、状态或决策。
- [ ] 动效不阻碍阅读，也不为了满足模板而添加。
- [ ] 移动端仍能读懂核心因果链。
- [ ] 每张展示素材都有说明其业务意义的图注，且完成必要脱敏。

## 10. 规范的最终判断标准

一个合格案例不是模块越多越好，而是读者看完后能够清楚回答：

1. 为什么必须改变？
2. 你发现了什么真正的根因？
3. 你做了哪些判断，为什么这样取舍？
4. 系统如何在真实组织中运行？
5. 结果如何被测量，哪些结论仍然有限？

最终要证明的是：

> **你能理解复杂业务，并通过产品判断建立可持续运行的系统。**
