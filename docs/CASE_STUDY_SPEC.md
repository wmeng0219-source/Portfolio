# 作品集案例内容规范

本文件是现有及未来案例的通用内容质量依据。审核稿从[文档入口](README.md)进入对应`content.md`；事实以`docs/project/`为准，原始材料仅用于追溯。协作顺序和文档职责见[AGENTS.md](../AGENTS.md)，通用视觉采用值见[DESIGN.md](../DESIGN.md)。

## 1. 案例需要证明什么

作品集定位是**具有设计背景的复杂业务系统产品经理**（Product Manager for Complex Systems, with a Design Background）。案例应让读者理解真实现场、规则与角色关系，看到可解释的产品判断、落地过程和可靠证据。界面、系统图与动效是证明判断的材料，不以页面或模块数量衡量质量。

### 1.1 内容底稿定位

案例的`docs/pages/<slug>/content.md`是唯一的完整案例叙事底稿，为后续页面信息设计提供可靠依据；不承担PRD、原始资料库、简单大纲或最终网页文案的职责。

保留理解项目和设计判断所需的背景、因果关系、方案细节与证据，内容充分但不追求业务规则全集，也不按网页字数提前压缩。正文与内部维护说明分开；来源、待确认项和简短覆盖检查留在底稿中，详细公式、完整异常分支与接口细节按需引用事实资料。

### 1.2 自由叙事与读者理解

- 根据项目自身的因果关系和重要设计判断组织章节，不固定章节数、顺序或亮点数量，不提前对应网页区块。第2节的十项是检查维度，不是章节模板。
- 先解释服务对象、业务对象、原有工作方式和改变的原因，再展开方案。术语首次出现时解释；典型场景须基于真实机制，不虚构客户经历、价格或引语。即使不看截图，陌生读者也应能理解。
- 围绕“问题及影响 → 判断依据与取舍 → 解决机制 → 变化及边界”说明关键设计。场景和功能用来支撑判断，不逐项罗列亮点，不预设固定判断链、额度池、人工分支或界面分区。
- 将业务关系解释为操作者需要确认什么、系统据什么处理、结果如何核对；涉及外部平台时说明依赖和限制。业务操作逻辑不能冒充接口执行顺序。
- 重要判断须有事实、真实设计记录、机制或界面支持，并注明证据能证明什么。区分本人工作、共同确认与团队决策；不补编调研方法、备选方案、测试或个人主导权。

## 2. 内容完整性检查

写第一稿前检查资料覆盖，完成后再次检查；同一段可覆盖多项，不为填表重复叙述。不适用或缺证据的内容如实标记，不强制增加反思、首屏战果或版本对比。

| 维度 | 应回答的问题 |
| --- | --- |
| 1. 项目概况 | 这是什么项目，面向谁，解决什么问题？ |
| 2. 业务背景 | 原有业务如何运作，为什么需要改变？ |
| 3. 问题与目标 | 关键问题、原因和影响是什么，希望实现什么变化？ |
| 4. 约束与取舍 | 有哪些业务、技术或组织限制，为什么选择当前方向？ |
| 5. 我的职责与协作 | 我实际负责什么，与哪些角色共同完成，决策边界是什么？ |
| 6. 分析与设计过程 | 如何发现、分析问题并形成判断，有哪些真实记录？ |
| 7. 关键设计方案 | 为什么这样设计，机制具体如何解决问题？ |
| 8. 落地与结果 | 如何进入使用，实际观察到什么变化，依据是什么？ |
| 9. 边界与反思 | 哪些问题未解决，有什么代价；反思是否真实且获准公开？ |
| 10. 证据与素材 | 重要结论有哪些数据、原始资料或真实界面支持，证明范围是什么？ |

### 2.1 事实与归因

- **已确认事实**：已上线功能、实际数据和已发生决策使用确定语气。
- **设计推理**：说明观察、访谈或规则分析依据，不能包装成用户研究结论。
- **假设与未验证方向**：明确标注，不写成已实现能力或成果。

不虚构研究、反馈、数据或失败，不把团队成果全部归为个人，不把相关性写成单一因果。隐私材料可匿名或概括来源类型，不能因不可公开而补编证据。

结果须回应设计目标，并分别说明**实际观察到的效果、已实现的系统能力、落地范围与使用反馈**。有额度限制或记录功能不等于已验证管理改善；推广不等于全员采纳，定性好评不等于留存统计。用户后续明确确认可修正旧资料，保留冲突来源，不将已确认口径反复列为问题。

### 2.2 数字与来源

每个公开数字保留已有且适用的口径，缺口明确留在证据入口，不用看似精确的结论掩盖不确定性。

| 字段 | 要求 |
| --- | --- |
| 指标名称 | 测量的对象和含义 |
| 分子/分母 | 转化率、完成率、检出率等比例必须区分 |
| 人群/样本 | 门店、患者、影像或交易类型等适用范围 |
| 时间范围 | 观察周期或前后对比时间 |
| 数据来源 | 埋点、报表、抽样、现场实测、人工统计或团队估算 |
| 归因限制 | 外部变量、样本限制，以及可以和不能支持的结论 |

口径不完整时使用准确的“约、阶段性数据、平均记录数”等表达，且保留限制。管理目标、使用规模与效果分别说明；不同单位或周期不串成漏斗。平均每张影像发现数增加不等于医学检出率提高，应区分发现数、召回率、准确率与漏诊率。现场实测和团队估算不能包装成同等级精确KPI。

“调研显示、一线反馈、上线后改善”等表述应能追溯来源、对象范围和时间。研究或试点有相关材料时，记录参与角色、任务、评价标准与据此形成的判断。

### 2.3 素材与图注

选择能证明现场、机制、判断或结果的素材，不以图片数量作为完成标准。每张图配就近图注，说明业务意义、来源范围及必要脱敏；关系示意不能冒充系统截图，缺图不能用装饰图或假产品证据补数。图示要有文字解释，不能用图替代推理。

界面稿可以证明信息组织和交互机制，不能单独证明实际使用、故障发生率或效率改善；虚构展示数据不作经营结果。缺少界面时可引用已确认事实或设计记录，并明确材料缺口。

### 2.4 文案与双语

- 当前按用户2026-10-15决定先完善PC中文，确认后再做移动端；英文暂停且非必需。暂停期间新增文字先做中文，不强制同步翻译；保留既有英文资料，未来启用时再按语境转译与审核。
- 标题优先帮助扫读；用途型、判断型标题按实际层级选择，不要求每个标题都是结论句。
- 每段聚焦一个因果关系，避免堆叠“系统化、闭环、赋能、提升”等抽象词。
- 不把目标写成结果、功能数量写成价值、个人推演写成上线故事。

### 2.5 缺失信息核对

先读当前底稿、事实资料、相关原始需求、用户已确认回答和证据清单，再识别缺口；不直接改写旧正文，也不默认遍读全部历史材料。

| 分类 | 处理 |
| --- | --- |
| 必须核对 | 不解决会影响业务理解、关键判断或事实准确性；先查现有来源，仍无法解答时集中询问少量关键问题，说明影响，不自行补全。 |
| 建议补充 | 能增强说服力但不阻碍故事成立；标注缺口，按已有事实继续成稿。 |
| 内部保留 | 具体公式、完整规则与接口细节等；仅将支撑核心判断的部分写入正文，其余留在事实资料。 |

不重复询问已确认问题，不把所有细节变成问卷；无阻碍核心叙事的缺口就直接生成完整底稿。

## 3. 按需增强

| 模块 | 何时适用 | 应呈现什么 |
| --- | --- | --- |
| Design Craft | 视觉或交互是项目价值的重要部分 | 色彩/组件的业务语义、认知负荷、渐进暴露、反馈容错与责任边界；不泛列设计参数 |
| 迭代与版本 | 存在真实演进和判断变化 | 阶段间为何调整及依据；无V1/V2时可写推进阶段或机制演进 |
| 系统模型 | 状态、权限、规则、数据或任务关系需要解释 | 已确认关系、异常与边界，配文字推理 |
| 界面走查 | 连续界面能证明关键决策 | 原有/新方案、正常/异常或端到端操作；不展示无论点的全量截图 |
| 研究与试点 | 有可回溯材料且与判断相关 | 观察、任务、反馈及它怎样改变决策 |
| 反思 | 有真实学习、未验证判断或可讨论的后续取舍，且获准公开 | 结论适用范围与重做时会先改变的判断；可融入结果或结尾，不编失败，不以“继续优化”代替具体学习 |

反思不是每个主案例的机械必填章。会员案例按用户决定暂不公开反思，待本人提供并确认后再加入；不能用本规范覆盖该决定。

项目类型决定展开重点：复杂业务系统重规则、状态、治理和角色协作；体验优化重研究、交互变化及验证；从0到1重机会、MVP和落地；AI与专业工具重人机责任、置信度、异常及专业控制权。具体案例事实与章节仍由对应内容稿决定。

## 4. 审核判断

完成后从**内容完整性**与**叙事理解质量**自检，并在正文之外附简短覆盖检查及关键缺口。验收标准为：

- **事实准确、可追溯**：事实、贡献和证据范围清楚，冲突与未知已标注。
- **信息充分、可独立阅读**：陌生读者不看截图也能理解业务、原有工作和核心问题，关键因果没有因压缩而缺失。
- **逻辑连贯、判断清楚**：问题、依据、选择、机制和变化自然相连，能看出本人贡献，避免功能拼接与重复解释。
- **结果客观**：观察效果与系统能力分开，并回应目标，明确适用范围和限制。

审核涵盖故事理解与事实证据；没有证据的过程或效果不补写。用户确认的版本作为后续依据，后续局部反馈定向修订，不主动重开整篇。内容确认后按授权进入页面信息设计，再决定视觉重点与文字取舍；底稿通过不等于页面设计或实现通过。
