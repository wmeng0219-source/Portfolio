# 接诊全流程预习与任务编排引擎

## 项目背景

在儿童齿科接诊场景中，患者到店前往往需要医生、护士、运营等多个角色提前协同。由于涉及初诊、复诊、特殊病史、多生牙、龋风险和不同会员类型，团队在正式接诊前就需要对患者情况形成较细颗粒度的共识。

但在过去，接诊前信息分散在多套系统中：家长诉求在网络电话系统、预约与收费在领健系统、既往病史和口腔检查表在患者 360 系统。信息孤岛导致团队很难在患者到店前形成统一目标，流程高度依赖人工沟通，容易出现漏项、协作脱节，以及续卡等商业机会流失。

## 项目目标

- 打破信息孤岛，建立统一的接诊前全景视图。
- 将复杂接诊过程拆解为结构化、可追踪的任务包。
- 让医、护、运协同从线下补位转为系统承接。
- 通过前置编排降低一线执行负担，并减少病历与备注的重复书写。

## 我的角色

我在该项目中的主身份是产品设计师，负责全链路的交互与体验设计。

但随着方案推进，我的工作边界逐步延伸到产品逻辑推演与规则收束。在高密度任务编排和复杂边界场景下，单纯线框图已经不足以覆盖诸如伴随动作、牙位选择互斥、多角色流转条件等真实问题，因此我进一步参与需求文档撰写，通过设计推导反向推动产品方案成形。

这个项目对我的价值不只是“做了一个复杂页面”，而是第一次系统性地把设计工作推进到产品逻辑、规则梳理和 PRD 共建层。

## 核心问题

- 接诊前信息分散在多套系统中，团队缺少统一视图，需要跨系统查阅和手工拼接信息。
- 医、护、运之间的协同主要依赖线下沟通，缺少线上承接机制，患者到店前难以对齐接诊目标。
- 接诊预习涉及任务包、具体任务、单选多选、牙位选择等多层结构，传统界面形式难以让一线快速理解和执行。
- 系统推荐动作背后依赖大量规则，若推荐理由不可解释，一线容易对系统判断产生抗拒，影响执行一致性。

## 关键方案

### 任务编排界面

我将复杂接诊流程重构为可排序、可折叠的任务包结构，让不同角色在统一页面中理解各自需要完成的动作。任务包支持拖拽排序、插入和折叠，空任务默认隐藏，避免一上来就把所有复杂度直接堆给一线人员。

在具体交互上，我把“任务包 -> 具体任务 -> 任务内选择 -> 牙位操作”这条高密度链路拆成分层可操作的结构，并为口腔场景定制了十字牙位选择器，以承接全口、象限和特殊牙位场景。这一方案解决的不是单纯排版问题，而是让复杂医疗规则第一次能被前台界面稳定承接。

### 系统推荐理由可解释化

在预习流程中，很多动作并非人工手动添加，而是系统基于既往就诊记录、间隔时间和病史条件自动推荐。如果只给出“系统建议做什么”，却不解释“为什么建议做”，一线很容易把它看成额外负担。

为此，我没有把底层规则直接铺在主界面，而是设计了抽屉式的推荐理由展示。用户在不打断主流程的前提下，可以按需查看系统如何推导出某个任务建议。这种处理方式兼顾了主流程清爽与系统可解释性，也反向促使产品把原本隐性的推荐规则整理为可被清楚说明的逻辑。

### 多角色流转与防卡点机制

为了让医、护、运的协同从“口头提醒”转向“系统承接”，我围绕角色流转设计了更明确的阻断与校验机制。每个角色都有对应的必填项，当流转失败时，系统会自动定位到首个未完成项并进行明确提示，减少长页面操作中的迷失和遗漏。

同时，我为预习流程增加了时效校验逻辑。当距离上次预习超过一定时间后，系统会要求重新确认，避免团队继续沿用过期方案接诊。这类设计表面上是交互防呆，实际解决的是多角色协同中的流程断点和责任不清问题。

## 推进与落地

该项目的推进难点不在单一页面设计，而在于复杂规则需要被逐步收束为可执行方案。随着设计深入，我开始通过需求文档和规则推演补齐线框图无法覆盖的边界场景，使方案从“界面草图”转向“可讨论、可确认、可落地”的产品方案。

对我来说，最关键的推进动作不是继续细化视觉稿，而是把设计过程中暴露出的复杂条件转译成产品可讨论的规则表达。这个过程让原本停留在交互层的问题，逐步收束为可进入 PRD 的明确逻辑，也让团队对系统如何承接任务编排、多角色协作和规则判断形成更一致的理解。

## 项目结果

- 建立了统一的接诊前预习视图，减少团队在患者到店前跨系统查找信息的成本。
- 将复杂接诊流程转为可承接的任务包机制，使接诊前准备从经验驱动转向结构化执行。
- 为医、护、运协同建立了更明确的线上推进路径，减少流程中对线下补位和临时沟通的依赖。
- 验证了我从产品设计深入到产品逻辑、规则整理和需求共建的能力，使该项目成为“设计驱动产品”能力的代表案例。
