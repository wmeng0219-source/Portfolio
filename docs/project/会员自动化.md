## 二、旧流程与问题

立项前，会员卡、卡券、收费账单和优惠都在领健一个系统内，但分属不同模块。前台办理升级时需要反复查找信息、手工计算差额和有效期，再处理原卡、新卡与权益；跨店升级还涉及账单归属和退款路径。（2026-10-27 用户确认：立项前会员操作都在领健一个系统内；两套系统是上线后的结果。）

### 2.1 为什么做这个项目

团队当时曾考虑过重新开发一套独立的门诊收费系统。但门诊收费不仅涉及会员开卡收费，还深度绑定了全门诊诊疗、预防、正畸等大量复杂项目的收费规则，如果整体重构，不仅开发周期漫长不可控，业务规则变更成本也过高。因此团队放弃重做收费系统，选择在现有门诊系统基础上，以最小成本、最快周期搭建外挂自动化层。

现场真实痛点来自**业务规则复杂性与系统割裂**：
1. 门店配有纸质收银手册，但现场前台运营面临极高的并发压力（一人同时处理挂号、开卡、打单、卖卡等四五件事），面对排队带娃的家长，根本来不及翻阅手册；
2. 原有门诊系统在收银时没有任何规则校验与限制，全靠前台人脑硬记；
3. 特殊折扣原本走钉钉审批，但审批流程长、收银场景紧急，前台通常只能通过电话向管理层口头确认后直接开卡改价，后续再补提审批。大量“先办后补”导致审批与账单脱节，财务月初核对上月账单时频繁面临违规优惠与账实不符。

**归因边界：** 这些是立项时的产品目标和现场问题，不等于项目已经达到的效率、合规或经营结果；具体成效见“结果口径”。

### 2.2 一次升级需要人工串起卡、账单和权益

旧流程的根本复杂性来自**数据结构与系统割裂**：
- **卡券结构割裂**：单年卡的权益一部分在会员卡本身，另一部分以卡券形式发放；囤卡也是以发券形式存在；多年卡的所有权益才在会员卡本身里。原系统内卡与券分散在不同模块、缺乏关联对应关系，升级退卡时极易漏算、漏退；
- **多维变动叠加**：孩子跨年龄导致卡种跳档，历史优惠券能否计入抵扣口径不一，跨门店升级涉及两店账单退补。熟练员工要算 4—5 分钟，新手遇到复杂账单甚至可能耗时十来分钟。开错账单、录错信息、账目对不上时常发生。

调研中的具体例子：一张 1 年卡用了 100 元券，升级到 5 年卡时，券能否继续抵扣会让差价相差 100 元；孩子快 6 岁时 5 岁卡和 6 岁卡可能同时出现；家里第二个孩子的 9 折按后办的卡算；老客介绍新客的券要分别发给老客和新客（`会员自动化前的调研-来自高高.md`、`2025年8月1日会员产设内审.md`）。

### 2.3 异常交易不能靠同一条默认流程处理

多张可用账单、没有可用账单、会员卡冻结、已过期、退卡或囤卡等情况，都会影响能否办理以及如何办理。旧流程依赖工作人员理解规则；常规交易与异常情况没有清晰分开，容易把边界场景留给个人经验。

跨店升级还涉及账单归属和退款方式；如果原卡退费与新卡收费没有对应好，后续核对会更难。这里不补写具体错误率、损失金额或发生次数，现有材料不支持这些量化结论。

### 2.4 优惠审批与月初核对

特殊折扣原本走钉钉审批，但审批流程长、收银场景紧急，前台通常通过电话向管理层口头确认后直接开卡改价，后续补提审批。这种“先办后补”导致审批与账单脱节，财务月初核对上月账单时频繁面临违规优惠与账实不符。

因此，项目将优惠从“事中笔笔审批”改为“事前额度池 + 刚性阻断 + 全链路审计”，流程彻底取消审批环节，消灭监管真空。

## 四、规则与策略演进

### 4.1 升级受理条件：不是所有升级都能办

**2026-10-28 用户确认：** 升级受理条件为**“有效期内即可”**。下列条文里的“距离到期 ≤3 个月”等表述来自未同步的旧文档（`会员卡系统规则.md`、`250811` PRD、冒烟测试），按本确认作废，仅保留追溯。该口径已定，不再就此询问用户；页面不展开具体条件。

- 长期卡：通常要求距离到期 ≤3 个月、且卡内还有项目；具体以现行规则为准。
- 次卡：有剩余项目时，不考虑是否过期都可升级；无剩余项目时，仅在有效期内可升级。
- 升级到金橙卡时，价格按原卡购买时年龄对应的卡价计算；距离生日 <4 个月时可买下一阶段（详见规则）。
- 不满足升级条件时按续卡处理，避免把续卡做成升级。

### 4.2 优惠治理：从逐笔审批到门诊/角色额度

旧方式下，优惠依赖人工审批：现场需要等待，审批也不等于建立了统一的系统边界。

新方案把门诊与角色的可用额度写入系统：额度内允许现场执行，超额则明确阻断并提示原因，同时记录执行人、时间和规则命中情况供财务追查。合规重点从“审批每一笔”转为“系统守住边界”；额度控制也不等于财务从此不需要核对。

**2026-10-28 用户确认机制：** 额度用完后，这笔不再给优惠，流程里没有审批环节；不存在“超额后再找人批”的路径。旧稿里“超额仍需复核”“异常申请审批”一类表述与现行机制不符。

现有材料没有提供具体额度数值、角色名单和权限配置，页面不补写金额或审批层级。

内部评审通知还提到“2—5 岁金橙卡免审批”“五年卡按生日自动调整”“卡券过期不用重发”“降级等于退卡再开卡”等常规规则；这些属于会议记录中的目标或变更，是否全部上线需逐项核对，不能整体写成已完成。

### 4.3 失败回退：保留原卡与原权益

升级会同时改变卡、资金和权益。如果旧卡已经失效、新卡却没有生效，即使现场操作变少，也会留下更难处理的状态。

方案要求升级失败时保留原卡与原权益，提示失败原因，并记录失败与回退结果；不能出现“旧卡已失效、新卡未生效”的半完成状态。真实失败样本、回退成功率和具体接口执行顺序仍待核查，页面不伪造失败日志或技术上的原子性承诺。

### 4.4 自动化边界：标准场景自动，异常场景人工

高频标准场景由系统匹配账单、计算差额和有效期，并衔接原卡处理、新卡开通与补差；信息不足或存在多种可能时，进入对应异常处理，不强行给出自动结果。

“自动处理”指已定义的标准路径，不等于所有交易都能无人处理；现有材料没有自动化覆盖率、失败率或人工干预比例，不能写成已量化的自动化成果。

## 五、核心机制

### 5.1 升级与续卡主流程

典型办理顺序：

1. 读取会员卡与收费账单；
2. 判断办理类型与条件（升级、续卡或退卡等）；
3. 匹配账单，计算差额、有效期与目标权益；
4. 校验优惠额度；
5. 展示原卡状态、差额、目标权益和限制原因，等待确认；
6. 执行办理，衔接原卡处理、新卡开通与补差；
7. 展示结果并留存记录。

单年卡、多年卡、长期卡、囤卡、优惠券和手动优惠按各自规则处理；跨店办理保留账单归属与变更记录。提交前展示待确认信息，成功后展示新旧卡关系、权益生效时间和账单归属，方便前台核对并向会员解释。

### 5.2 卡、账单与权益的对应

会员卡、卡券、收费账单和权益需要一起核对。系统统一处理升级前后的卡关系、账单归属和权益承接，并记录每次办理前后的变化；成功反馈说明当前结果，操作记录用于追查结果如何产生。

跨店结算仍依赖底层系统和批处理，不能把本项目描述为实时分账。具体接口调用顺序、重复提交防护和异常补偿机制仍需核查，不在页面补写技术实现。

### 5.3 优惠额度与审计

优惠按门诊与角色额度校验。额度内允许现场执行；超额则阻断并说明原因，取代逐笔等待人工审批的方式。系统记录执行人、时间、规则命中情况，便于财务追查。

额度治理约束的是优惠范围，不是所有财务核对；页面不写具体额度、审批人或“完全取代人工审批”。

### 5.4 操作留痕

记录执行人、时间、规则命中、失败原因和回退结果，支持门店交接、财务核对和后续追查。留痕是“可追查”的基础，不等于已经证明所有操作都被正确执行；实际审计效果、异常发生量和门店采纳情况仍缺统计。

### 5.5 交互与设计取舍

- **高频场景聚焦：** 默认路径只展示完成典型升级所需的信息，减少页面往返。
- **即时校验：** 提交前显示原卡状态、差额、目标权益和限制原因，降低收银员心算负担。
- **渐进式暴露：** 只有出现多账单、无账单、额度不足或冻结等情况时，才展开异常处理选项。
- **结果反馈：** 成功后明确展示新旧卡关系、权益生效时间和账单归属。
- **失败回退：** 失败时保留原卡与原权益，并记录原因和回退结果。

这些是设计判断和方案事实；现有材料没有点击次数、操作耗时对比或所有门店的采纳统计，不能写成已量化提效。

### 5.6 上线后的系统分工（项目结果）

项目没有替换领健。上线后，会员卡和优惠券的操作在 ODOS，收费单和就诊记录仍在领健；ODOS 通过接口调用领健完成收费、开卡、退费、改有效期。前台需要在两个系统之间衔接。

不是所有会员卡都在 ODOS 开通。选择升级时，如果原卡不是在 ODOS 开通的，可能出现多张收费单，或者找不到对应收费单，需要人工选择、核对（`收银补充手册（ODOS试行版）.md`）。跨店升级还要原门店退费、新门店开卡、原门店补差价，两个门店的收费系统分别处理（`250811-会员系统-需求文档.md`）。

这是项目选择“自动化层而不是替换领健”的结果，也是当前操作边界；不是立项原因。第二章的旧流程描述的是立项前会员操作都在领健一个系统内的阶段。

## 六、异常边界

| 情况 | 处理边界 |
| --- | --- |
| 多张可用账单或无可用账单 | 进入对应异常处理，不强行自动匹配；页面不补写具体规则数量 |
| 会员卡冻结、已过期 | 按卡状态限制办理，并说明原因；解冻、退款到账等细节未展开 |
| 优惠额度不足或超额 | 阻断本次操作，提示额度原因；不展示虚构额度或审批记录 |
| 升级执行失败 | 保留原卡与原权益，提示并记录失败原因与回退结果；真实失败样本仍待补 |
| 跨店办理 | 保留账单归属与变更记录；结算仍按底层系统规则处理，不是实时分账 |
| 退卡、囤卡、共享人 | 现有材料主要支撑升级场景；退卡金额计算、审批打款、冻结解除等细节不扩写 |
| 重复提交 | 属于需要防护的边界，具体实现与验证材料仍待核对 |

页面可以说明“异常有对应处理路径”，但不能写成“所有异常都已覆盖”或“失败都能自动恢复”。

## 七、结果口径

### 7.1 典型会员升级耗时

- **观察：** 4—5 分钟 → 约 1 分钟。
- **来源：** 门店现场实测，典型升级结算场景。
- **限制：** 不是所有交易的平均耗时；计时起止动作、门店、样本量和观察时间未提供。页面应写“典型场景”，不能写“平均提效”或“全场景”。

### 7.2 财务对账耗时

- **观察：** 约 3 天 → 约 1 天。
- **来源：** 财务团队估算，未做精细统计。
- **限制：** 对应任务、周期和样本未提供；只作为辅助反馈，不作为首屏核心成果，也不与现场实测混为同一种证据。

### 7.3 上线范围

既有事实记录为全门店上线；未提供门店数量、逐店采纳率和规范执行率。累计或汇总量不能证明每家门店都在使用，页面不补写“100% 覆盖”。

### 7.4 不能声称的结论

现有证据不支持以下表述：

- 全场景平均提效、所有交易都变快；
- 财务对账已完全自动化、实时分账或全面取代人工核对；
- 续卡率、现金流或初诊转化由本项目单独带来；
- 所有门店均已采纳、所有异常都已覆盖、失败都能自动恢复；
- 具体额度、审批层级、接口性能或重复提交防护已经验证。
