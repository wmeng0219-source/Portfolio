# 项目事实与作品集案例规范 (Project Documentation Standard)

## 目录定位

本目录用于沉淀真实项目事实、设计过程及作品集案例内容。

目录包含两个层级：

```

```

```
docs/project/
项目事实库（Project Fact Base）

docs/site/
作品集展示案例（Portfolio Case Study）
```

其中：

- `project/` 是唯一事实来源（Single Source of Truth） 
- `site/` 是基于事实加工后的展示版本 
-  所有作品集内容必须能够追溯到真实项目事实 

---

# 一、核心原则 (Core Principles)

## 1. 事实优先，而非叙事优先

作品集不是重新创造项目故事。

所有内容必须区分：

### 已确认事实

例如：

-  已上线功能 
-  实际业务流程 
-  真实数据 
-  已发生决策 

### 设计推理

例如：

-  为什么取消快筛 
-  为什么设计状态模型 
-  为什么调整流程 

### 假设与未验证方向

例如：

-  后续优化方向 
-  未上线方案 
-  待确认规则 

禁止将：

> 推测、讨论过程、未来规划

包装成：

> 已完成设计成果。

---

## 2. 展示重点：设计价值，而非功能列表

避免：

```

```

```
完成XX页面设计
开发XX功能
增加XX字段
```

转化为：

```

```

```
发现什么业务问题？

为什么采用这个方案？

如何通过设计解决？

产生什么业务影响？
```

# 二、案例类型判断

不同项目根据核心能力选择重点。

## A. 复杂业务系统 / B端产品

例如：

-  医疗 SaaS 
-  ERP 
-  CRM 
-  管理后台 

采用：

10步黄金结构。

重点：

-  业务理解 
-  流程设计 
-  状态模型 
-  角色协作 
-  系统机制 

---

## B. 用户体验优化项目

重点：

-  用户研究 
-  使用痛点 
-  体验问题 
-  交互优化 
-  可用性验证 

---

## C. 从0到1产品建设

重点：

-  机会发现 
-  产品定位 
-  MVP设计 
-  验证过程 
-  迭代结果

# 三、高级 Product Designer / ITBP 案例结构

适用于：

> B端系统重构、业务流程设计、复杂规则系统项目。

---

# 01 项目摘要 Executive Summary

目标：

首屏 3 秒理解项目价值。

必须包含：

## 项目定位

格式：

```

```

```
通过 [设计方法]
将 [旧业务模式]
转化为 [新业务机制]
```

## 我的角色

例如：

```

```

```
Product Designer / ITBP
```

## 核心职责

根据实际情况选择：

-  用户研究 
-  业务流程梳理 
-  信息架构设计 
-  状态模型设计 
-  交互设计 
-  UI设计 
-  数据指标设计 
-  推动落地 

## 项目成果

优先表达：

业务变化：

↓

系统能力：

↓

数据结果

---

# 02 背景与业务挑战 Business Challenge

目标：

回答：

> 为什么必须改变？

包含：

## 商业背景

说明：

-  业务战略价值 
-  用户价值 
-  商业模式 

## 原模式问题

不要描述：

“页面不好用”

而描述：

系统级问题：

-  流程断裂 
-  信息孤岛 
-  依赖人工经验 
-  无法规模化复制 

---

# 03 问题发现 Problem Discovery

展示问题分析能力。

推荐结构：

## 研究方式

-  流程观察 
-  数据分析 
-  系统分析 

## 核心洞察

最多3-5个。

```

```

```

↓

根因

↓

影响
```

# 四、AI辅助整理规范

AI处理项目资料时：

## 应该做：

✅ 提炼结构

✅ 发现设计决策

✅ 提炼价值表达

✅ 帮助压缩内容

---

## 禁止做：

❌ 虚构用户调研

❌ 虚构数据

❌ 放大个人贡献

❌ 将团队成果全部归为个人

❌ 将讨论方案写成已上线功能

❌ 将业务目标包装成设计成果

---

# 五、最终输出标准

优秀案例应该回答五个问题：

1.  为什么做？ 
2.  发现了什么问题？ 
3.  为什么这样设计？ 
4.  如何落地？ 
5.  带来了什么价值？ 

最终目标：

不是展示：

> 做了多少页面。

而是证明：

> 能理解复杂业务，并通过设计建立可持续运行的系统。

# 六、内容就绪度与事实回填

项目主文档说明“已经确认的项目事实”；`content-readiness.md` 说明“进入案例页前还需要补齐哪些证据”。两者不能混用。

## 1. 回填顺序

每次补充项目材料，按以下顺序处理：

1. 将原始 PRD、报表、会议纪要、截图或访谈记录归档到 `docs/origin/` 或 `docs/design/`。
2. 在对应项目主文档中补充已确认的事实、来源、角色边界或判断。
3. 在 `content-readiness.md` 把相应待补项更新为“已具备”，并附上来源路径。
4. 只有事实层完整后，才更新 `docs/site/` 或页面内容。

## 2. 每个项目应收集的最小证据包

| 证据 | 最低要求 | 不能替代它的内容 |
| --- | --- | --- |
| 责任边界 | 周期、团队/协作角色、本人决策与交付边界 | 只有职位名称 |
| 指标口径 | 指标定义、样本、周期、来源、归因边界 | 单独的前后数字 |
| 决策记录 | 方案 A/B、选择标准、代价、异常兜底 | 只有最终方案描述 |
| 研究/验证 | 观察、访谈、报表、试点或反馈的来源范围 | “调研显示”式结论 |
| 素材 | 能证明问题、机制、结果的脱敏材料与图注 | 只有封面或装饰图 |
| 反思 | 已验证、未验证、限制与下次改变 | 泛泛的“持续优化” |

## 3. 与案例规范的关系

- `../CASE_STUDY_SPEC.md`：规定案例如何组织和验收。
- `content-readiness.md`：逐项目追踪证据缺口，不生成页面文案。
- 项目主文档：记录最终确认并可引用的项目事实。
- `../site/content-map.md`：决定已确认事实是否适合进入首页或详情页。
